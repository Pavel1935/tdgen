Про Swagger, API и взрослую возню

Сначала tdgen просто читал JSON-схему и делал негативные payload’ы.

Это уже полезно.
Но всё ещё немного тепличная история.

Потому что в реальном проекте данные не просто лежат в файлике и ждут, пока их кто-то обидит. Они летят в API. API валидирует. Иногда валидирует нормально. Иногда делает вид, что всё хорошо, хотя на вход прилетел откровенный мусор.

Захотелось проверить tdgen не в вакууме, а в условиях, похожих на нормальную работу.

Поэтому рядом появился demo API на FastAPI.

Не продукт.
Не стартап.
Не “архитектурное решение”.
Просто маленький endpoint `POST /users`, который можно долбить плохими payload’ами и смотреть, где система начинает течь.

Что теперь есть

`demo_api/app.py` - маленький API для проверки payload’ов.  
`openapi.json` - Swagger/OpenAPI-контракт.  
`openapi_to_tdgen_schema.py` - переводчик из Swagger в схему для tdgen.  
`schemas/user_from_openapi.json` - схема, полученная из контракта.  
`output/payload_from_openapi.json` - негативные данные, которые tdgen сгенерировал сам.  
`tests/test_users_negative_from_openapi.py` - pytest, который гонит всё это добро в API.  
`prompt_builder.py` - сборщик промпта для разбора падений через AI.

Как это работает

Запускаем API:

```bash
uvicorn demo_api.app:app --reload
```

Swagger живёт здесь:

```text
http://127.0.0.1:8000/docs
```

Забираем OpenAPI-контракт:

```bash
curl http://127.0.0.1:8000/openapi.json -o openapi.json
```

Конвертируем контракт в схему для tdgen:

```bash
python3 openapi_to_tdgen_schema.py
```

Генерируем негативные payload’ы:

```bash
python3 tdgen.py --schema schemas/user_from_openapi.json --out output/payload_from_openapi.json
```

Запускаем тесты:

```bash
pytest tests/test_users_negative_from_openapi.py -v
```

Если всё нормально, получаем:

```text
10 passed
```

Что это даёт

Раньше правила можно было руками написать в `user.json`.

Теперь правила берутся из API-контракта.

То есть если в контракте сказано:

password минимум 8 символов

tdgen делает payload с password на 7 символов.

Если завтра минимум станет 10, tdgen не надо уговаривать, гладить по голове и переписывать руками. Достаточно обновить контракт и пересобрать payload’ы.

Вот ради этого всё и затевалось.

Не чтобы “AI заменил тестировщика”.
Не чтобы “автоматизация сама всё поняла”.
А чтобы не плодить одну и ту же херню в трёх местах.

Что ломаем

email без `@`.
пустой email.
отсутствующий email.
email из одних пробелов.
email с пробелами по краям.
слишком длинный email.
password короче минимума.
пустой password.
password из пробелов.
слишком длинный password.

Один payload ломает одно правило.
Остальные поля остаются валидными.

Без комбинаторного ада.
Без “а давай ещё логин валидный, пароль невалидный, но email грустный”.
Эта каша пусть живёт в отдельных тестах.

Про API-ответы

API должен не просто сказать “400”.

Потому что “400” без нормального тела ответа - это как разработчик, который говорит “у меня работает” и уходит пить кофе.

Нормальная ошибка выглядит так:

```json
{
  "error": "validation_error",
  "field": "password",
  "message": "String should have at least 8 characters"
}
```

Тест проверяет не только статус.
Он проверяет, что API вернул нормальный error response, а не какой-то JSON-обрубок, от которого хочется выйти из профессии.

Про PromptBuilder

Когда тест падает, начинается любимое:

что упало?
на чём упало?
какой payload?
что вернул API?
это баг теста или backend опять решил быть особенным?

Чтобы не собирать это руками как бедолага, добавлен `PromptBuilder`.

Он берёт:

endpoint.
payload.
expected status.
actual status.
response body.

И собирает из этого нормальный prompt для AI-разбора.

Пример:

```text
ENDPOINT:
POST http://127.0.0.1:8000/users

PAYLOAD:
{
  "email": "email@email.com",
  "password": "ValidPass123"
}

EXPECTED STATUS:
400

ACTUAL RESPONSE:
Status: 200
Body:
{
  "id": 1,
  "email": "email@email.com",
  "is_active": true
}
```

AI тут не волшебник.
Он просто получает нормальный контекст, а не крик души “всё упало, я в говне”.

Итог

tdgen начинался как генератор негативных данных.

Теперь вокруг него есть минимальный, но честный workflow:

```text
OpenAPI
-> schema для tdgen
-> negative payloads
-> pytest
-> проверка ответа API
-> prompt для разбора падения
```

Всё ещё маленький pet-проект.

Но уже не просто скрипт, который делает JSON’чики.
Теперь он берёт контракт, генерит плохие данные, бьёт ими API и показывает, где система начинает вести себя как кусок говна.
